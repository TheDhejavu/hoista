A server of your own (a Hetzner Cloud server, for now) costs a few euros a month and runs whatever you put on it. An agent can set it up for you: install what your app needs, write a Docker Compose file, put a reverse proxy in front, or add a GitHub Actions workflow that deploys on every push.

Hoista is how the agent gets in. It makes the server, keeps its SSH key in your keychain, and signs in on the agent's behalf. The agent never sees the key, everything it does is in **Activity**, and anything risky waits for you.

Hoista doesn't deploy to the server itself. How your app gets there is up to you and your agent.

## Make the server

Connect a [Hetzner](/providers/hetzner) project, then in a project choose **Add server**, or ask your agent:

> Make a small Hetzner server for this project in Falkenstein, call it web-1.

It's ready for the agent once its setup has finished, a few minutes after it starts: until then it shows as deploying in the project, and `server_status` says where it is.

## What the agent can do

| Tool | What it does | View only | Ask for approval | Full access |
| --- | --- | --- | --- | --- |
| `server_status` | setup, load, memory, disk, failed services, containers, waiting updates, whether a reboot is due | yes | yes | yes |
| `server_logs` | the newest lines of a systemd unit, a Docker container or the whole journal, between two times, or new lines for up to a minute | yes | yes | yes |
| `server_read_file` | one file, up to 1 MB | yes | yes | yes |
| `server_run` | one command, as `hoista`, who can use `sudo` | no | asks each time | asks, unless you turned that off for this server |
| `server_write_file` | one file, with its mode and owner | no | asks each time | asks, unless you turned that off for this server |
| `server_deploy_key` | a key for CI that can run only one command | no | asks | asks |

Everything done on a server (commands, files written, deploy keys, its setup) is listed on its **Settings** tab under **Agents → Activity**, as well as in the project's Activity.

What comes back from the server goes through Hoista's secret scanner first, as logs do. Password hashes, private keys and other processes' environments are never read, wherever a link points.

## When it asks you

With **Ask for approval**, every command and every file waits for you. With **Full access**, they still do until you change it for that server: open the server, then **Settings → Agents → Agents with Full access**, and choose **Don't ask**. Hoista asks you to confirm it's you first.

Some steps ask you whatever that setting says, because they can lock you out or can't be undone:

- deleting system folders (`rm -rf` on `/`, `/etc`, `/usr` and the like), formatting or overwriting disks;
- changing the firewall (`ufw`, `iptables`, `nft`), SSH, users, groups, passwords, `sudo` or `authorized_keys`;
- rebooting or shutting down;
- writing files under `/etc/ssh`, `~/.ssh`, `/etc/sudoers.d`, `/etc/pam.d` or `/boot`.

This list catches mistakes; it isn't a sandbox. If you don't want an agent to have a shell on a server at all, keep it on **Ask for approval** or **View only**, or limit it to some projects in **Agents**.

## Examples

**Docker Compose.** Ask the agent to run your app with Compose behind Caddy. It typically writes `/srv/app/compose.yaml` and a `Caddyfile` with `server_write_file`, then runs `docker compose up -d` in `/srv/app` with `server_run`, and checks `server_logs` for the containers. Secrets go in a `.env` file written with mode `600`.

**Deploy on every push.** Ask the agent to set up GitHub Actions. It writes a deploy script on the server (say `/srv/app/deploy.sh`, which pulls and restarts), makes a key with `server_deploy_key` that can run only that script, and adds the key to the repository's Actions secrets. A leaked CI secret can then run your deploy script and nothing else.

## Limits

- Agents reach only servers Hoista made, and only through Hoista on your computer, not a remote Hoista.
- Each tool call is one command, up to 15 minutes, with up to 64 KB of output kept. For long jobs, have the agent start them in the background (a systemd unit or `docker compose up -d`) and read the logs after.
- The server's IP address can be seen on the server's page. If you rebuild the server outside Hoista, its host key changes and Hoista refuses to connect until you make it again.
